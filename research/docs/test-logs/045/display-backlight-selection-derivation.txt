Q1. Which device does OUR code read, and by what selection logic?
--------------------------------------------------------------------

Code: `src/providers/mod.rs:360-369` `discover_display_backlight_path()`:
  pub fn discover_display_backlight_path() -> anyhow::Result<PathBuf> {
      for entry in std::fs::read_dir("/sys/class/backlight/")? {
          let entry = entry?;
          let name = entry.file_name().to_string_lossy().to_string();
          if DISPLAY_BACKLIGHT_NAMES.iter().any(|s| name.contains(s)) {
              return Ok(entry.path());
          }
      }
      anyhow::bail!("No display backlight found")
  }

Name list (`src/providers/mod.rs:327-332`):
  const DISPLAY_BACKLIGHT_NAMES: &[&str] = &[
      "apple-panel-bl",
      "gmux_backlight",
      "intel_backlight",
      "acpi_video0",
  ];

Selection logic: **scan `/sys/class/backlight/` in readdir order, return the
FIRST entry whose name `contains` any of the four DISPLAY_BACKLIGHT_NAMES
substrings.** The match is a SUBSTRING match (`name.contains(s)`), not an
exact match. The list order is the PREFERENCE order only insofar as readdir
order + first-match-wins — i.e. the ACTUAL device selected is the
first-in-readdir whose name contains ANY of the four names, NOT the first
name-in-the-list that matches. (If both `intel_backlight` and `acpi_video0`
existed, whichever readdir returns first would win; the list order is not a
priority order because the `.iter().any()` tests each entry against all four
names at once.)

Called from: `src/providers/backlight.rs:65` in `SysfsBacklight::new`:
  let display_bl_path = crate::providers::discover_display_backlight_path().ok();
The `.ok()` means a failure to find a display backlight is NON-fatal: the
curve falls back to `max_bl / 2` (`backlight.rs:183-185` in `update()`:
  .unwrap_or(self.max_bl / 2)
). So a missing display backlight degrades the curve to a mid-level default,
it does NOT panic.

The curve's denominator 509 is HARDCODED (`src/providers/backlight.rs:16`:
  const MAX_DISPLAY_BRIGHTNESS: u32 = 509;
), NOT read from the device's `max_brightness`. This is a fixed constant of
the display_to_touchbar curve (ported byte-identical from the oracle — see
Q2). On this bench `acpi_video0` reports `max_brightness=90`, but the curve
divides by 509, NOT 90 — so `display_bl=90` is interpreted as "90/509 of full
scale", i.e. the curve treats 90 as a lowish absolute level and yields 54.
This is BY DESIGN (the 509 is the Intel-panel full-scale that the original
tiny-dfr targeted; acpi_video0's own max of 90 is irrelevant to the curve).

On THIS bench, `/sys/class/backlight/` contains exactly two entries:
  acpi_video0      (i915, the main display)
  appletb_backlight (appletbdrm, the Touch Bar)
readdir returns them in name-sorted order on this fs (verified:
`python3 -c "import os; print([e.name for e in sorted(os.scandir('/sys/class/backlight/'), key=lambda x: x.name)])"` → `['acpi_video0', 'appletb_backlight']`).
`acpi_video0` matches `DISPLAY_BACKLIGHT_NAMES` (`"acpi_video0"` substring) →
selected on the FIRST iteration. `appletb_backlight` is NOT in the display
list (it is in `TOUCHBAR_BACKLIGHT_NAMES`, a separate list for
`discover_backlight_path`).

**Verdict Q1: OUR code reads `/sys/class/backlight/acpi_video0/brightness`.
Live reading at 01:45:00: brightness=90, max=90 (the max is NOT used by the
curve — the denominator is the hardcoded 509).**

Q2. Which device does the ORACLE read, and does it use the udev alias?
--------------------------------------------------------------------

Oracle code: `backup_old/tiny-dfr-mbp142/src/backlight.rs:46-62`
`find_display_backlight()`:
  fn find_display_backlight() -> Result<PathBuf> {
      for entry in fs::read_dir("/sys/class/backlight/")? {
          let entry = entry?;
          if [
              "apple-panel-bl",
              "gmux_backlight",
              "intel_backlight",
              "acpi_video0",
          ]
          .iter()
          .any(|s| entry.file_name().to_string_lossy().contains(s))
          {
              return Ok(entry.path());
          }
      }
      Err(anyhow!("No Built-in Retina Display backlight device found"))
  }

This is BYTE-IDENTICAL logic to our `discover_display_backlight_path` — the
SAME four names, the SAME substring match, the SAME readdir-scan-first-match
order. The port copied this function verbatim (ADR-048 §3c notes the curve
is byte-identical; the discovery function is too).

The oracle does NOT open the `tiny_dfr_mbp142_display_backlight` udev alias
node. The udev rules (`backup_old/tiny-dfr-mbp142/etc/udev/rules.d/99-
touchbar-tiny-dfr-mbp142.rules:14-17`) TAG four backlight KERNEL names
(apple-panel-bl, gmux_backlight, intel_backlight, acpi_video0) with
`ENV{SYSTEMD_ALIAS}="/dev/tiny_dfr_mbp142_display_backlight"`. This alias is
a SYSTEMD device-unit alias (used by `tiny-dfr-mbp142.service`'s
`Requires=/BindsTo=`/device dependency, IF the unit had one — the deployed
unit `backup_old/systemd/tiny-dfr-mbp142.service:1-22` does NOT reference it;
the alias is informational/for future device-unit gating). The oracle's
runtime code (`find_display_backlight`) scans `/sys/class/backlight/`
directly and does NOT consume the alias. So the alias is irrelevant to which
device the oracle reads at runtime.

On THIS bench, the alias is claimed by `acpi_video0` (the only one of the
four names present). Confirmed:
  $ systemctl list-units --all --no-pager | grep tiny_dfr_mbp142
  dev-tiny_dfr_mbp142_display.device        loaded active plugged /dev/tiny_dfr_mbp142_display
  dev-tiny_dfr_mbp142_display_backlight.device loaded active plugged /dev/tiny_dfr_mbp142_display_backlight
The `/dev/tiny_dfr_mbp142_display_backlight` symlink does NOT exist in /dev
(the alias is a systemd unit alias, not a /dev symlink — `ls /dev/tiny_dfr_mbp142_*` → no such file). The systemd device unit
`dev-tiny_dfr_mbp142_display_backlight.device` is the udev-TAGGED
`acpi_video0` backlight device (the sole match on this bench).

**Verdict Q2: the ORACLE reads the SAME device as our code —
`/sys/class/backlight/acpi_video0/brightness` — via byte-identical scan
logic. The udev alias is a systemd device-unit alias, NOT a runtime path the
oracle opens; it is claimed by acpi_video0 on this bench (the sole matching
name).**

Q3. Do the selections differ? Any finding?
--------------------------------------------------------------------

**NO — the selections are IDENTICAL.** Both our code and the oracle scan
`/sys/class/backlight/` for the first name containing any of
{apple-panel-bl, gmux_backlight, intel_backlight, acpi_video0} (substring
match, readdir order). On this bench both resolve to `acpi_video0`. The
curve's denominator 509 is hardcoded in BOTH (the oracle:
`backup_old/tiny-dfr-mbp142/src/backlight.rs:96-101` uses the same
`display as f64 / 509.0`; our port: `backlight.rs:160`). No selection
divergence, no scale mismatch between the two runtimes on this bench.

**No finding (ADR-050 candidate) is warranted on selection grounds: the two
runtimes read the same device with the same curve.**

NOTE (for the record, not a finding): the 509-vs-acpi_video0-max-90
"mismatch" is NOT a port bug — it is the upstream tiny-dfr design (the 509
is the Intel-panel full-scale the original targeted; on benches where the
display backlight is acpi_video0 with a lower max, the curve simply maps the
absolute acpi_video0 value through sqrt(val/509), treating it as a fraction
of the original full-scale). Both runtimes do this identically. This is
documented behavior, not a divergence. (If a future bench had
intel_backlight with max 509, the curve would behave "as designed"; on
acpi_video0 benches the bar runs a bit dimmer at a given acpi_video0 level,
but identically to the oracle.)
