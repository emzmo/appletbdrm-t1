=== STEP 1 scope decision — move-aside + mask ===
Timestamp: 2026-09-27T01:47:10+01:00 (decision received)

Blocker: `systemctl mask --now tiny-dfr-mbp142.service` FAILED —
`Failed to mask unit: File '/etc/systemd/system/tiny-dfr-mbp142.service'
already exists`. The oracle's deployed unit is a REAL FILE at
`/etc/systemd/system/tiny-dfr-mbp142.service` (not a symlink, not at
/usr/lib). It is byte-identical to the repo's
`backup_old/systemd/tiny-dfr-mbp142.service` reference (diff empty) — it IS
the oracle's canonical unit, just deployed at /etc. ADR-049's text
referenced `/usr/lib/systemd/system/tiny-dfr-mbp142.service` which does NOT
exist on this bench; the actual deployed path is `/etc/systemd/system/`.

`systemctl mask` creates a symlink
`/etc/systemd/system/<unit> → /dev/null` but refuses to overwrite an existing
real file at that path. The standard procedure to mask in this situation:
back up the real file, replace with the /dev/null symlink, daemon-reload;
reverse at STEP 8.

Human decision (VERBATIM, typed): "Authorize move-aside + mask (Recommended)"

Rationale (recorded for the audit): the /etc unit file is byte-identical to
the repo's backup_old/systemd/tiny-dfr-mbp142.service reference, so no
operator config is lost by the move-aside; the move is fully reversible
(rm the symlink, move the backup back, daemon-reload, unmask + start). This
is within the spirit of the controlled exception (mask/unmask the oracle for
the validation window) and is necessary because the oracle's unit lives at
/etc on this bench. The literal `systemctl mask` verb alone is insufficient
here; the move-aside is the mechanical means to achieve the mask.

Procedure to perform (STEP 1):
  1. Back up: `sudo cp -a /etc/systemd/system/tiny-dfr-mbp142.service
     /etc/systemd/system/tiny-dfr-mbp142.service.pre-045`
  2. Remove the real file: `sudo rm /etc/systemd/system/tiny-dfr-mbp142.service`
  3. Create the mask symlink: `sudo ln -s /dev/null
     /etc/systemd/system/tiny-dfr-mbp142.service`
  4. `sudo systemctl daemon-reload`
  5. `sudo systemctl stop tiny-dfr-mbp142.service` (stop the current activation)
  6. Verify: is-active=inactive, is-enabled=masked, /etc symlink → /dev/null.
  7. ADR-049 assertion: NO auto-restart within +60s (sleep 60, re-check
     is-active=inactive).
  8. Debugfs: touchbar card empty (no master row).

Procedure to reverse (STEP 8):
  1. `sudo rm /etc/systemd/system/tiny-dfr-mbp142.service` (the /dev/null symlink)
  2. `sudo cp -a /etc/systemd/system/tiny-dfr-mbp142.service.pre-045
     /etc/systemd/system/tiny-dfr-mbp142.service`
  3. `sudo systemctl daemon-reload`
  4. `sudo systemctl unmask tiny-dfr-mbp142.service` (no-op if the symlink is
     already gone, but run it for cleanliness)
  5. `sudo systemctl start tiny-dfr-mbp142.service`
  6. Verify: is-active=active, is-enabled=static, master on card2.
  7. Remove the .pre-045 backup (state fully restored to pre-session).

FINDING (for the record, ADR-050 candidate — not fixed on the air): the
oracle's deployed unit lives at `/etc/systemd/system/tiny-dfr-mbp142.service`
on this bench, NOT at `/usr/lib/systemd/system/` as ADR-049's text assumed.
`systemctl mask` cannot overwrite a real file, so the ADR-049 runbook
commands (`sudo systemctl mask --now tiny-dfr-mbp142.service`) FAIL on this
deployment shape. The runbook should document the move-aside procedure for
the /etc-deployed-unit case, OR the oracle should be redeployed to
/usr/lib (out of scope). Tracked as a runbook amendment, not a code fix.
