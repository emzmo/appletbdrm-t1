## INTERLOCK DISCOVERY — oracle auto-restarted DURING the tbard run
While tbard was running (before STEP 6), the oracle (tiny-dfr-mbp142.service,
is-enabled=static) self-restarted and panicked on the busy card, then entered
systemd's restart loop. Timeline (from tiny-dfr-mbp142 journal):

  Sep 27 00:38:03.547  tiny-dfr-mbp142[364955]: waiting for touchbar card (30/30)

This means the oracle was NOT actually stopped for the full duration of the
tbard run (STEP 1 → STEP 6). It was stopped at STEP 1 (23:43:28), but at some
point between then and 00:38:05 it was restarted (likely by a systemd trigger —
the unit is static + has a Restart= policy; possibly a socket/dependency or a
manual restart). It then spun in its 30s retry loop panicking on the busy card
(card2 held by tbard) until tbard released it.

  - The HC2 observation (item 4, first pixels) is VALID — tbard was sole master

  - The input diagnostic (evtest) is VALID — tbard held master.

NEW INTERLOCK FINDING (FREEZE — ADR proposal):
  The oracle (static + Restart=) does NOT stay stopped when `systemctl stop` is
  issued. It self-restarts and spins in a panic-retry loop against the busy
  card. This is a RACE in the interlock: the oracle's restart policy can fire
  while tbard is running, producing repeated panics (exit 101) in the oracle's
  journal and potentially tripping systemd's StartLimit if sustained. For
  Stage-3 validation this was benign (tbard held master throughout), but for a
  MIGRATION run it would be a problem — the oracle must be MASKED or have its
  Restart suppressed during tbard's run, not just stopped. See ADR proposal
  below.

  Also note: the oracle panicked at src/main.rs:839:21 with "touchbar card
  never appeared" — this is the oracle's OWN code (backup_old/tiny-dfr-mbp142/),
  not tbard's. The 30s retry (30/30) then panic is the oracle's busy-card
  behavior. Worth documenting for the migration plan.

## ADR proposal (interlock finding)
- ADR-049 (proposed): oracle masking during tbard validation/migration runs.
  `systemctl stop` is insufficient — the oracle's Restart= policy (static unit)
  self-restarts it, producing panic-retry loops against the busy card. For
  validation: use `systemctl mask` or `systemctl stop` + verify no auto-restart
  within +60s before starting tbard. For migration: the oracle's unit must be
  masked/disabled-by-policy before tbard takes over, or the Restart= policy
  must be removed. Coordinate with the interlock design (ADR-019).
