# Input diagnostic — finding (a) empirical corroboration
# Session 043, post-HC2

## objective
Determine whether the digitizer hardware produces valid touch events at the
kernel/libinput layer (below tbard's code), proving the touch-drop is in tbard,
not in the hardware.

## method
- Read-only, NON-EXCLUSIVE evtest capture on /dev/input/event7 (digitizer,
  iBridge). No --grab (does NOT block tbard from reading the same device).
- Human touched the bar once during a 25s capture window (HC confirmed:
  "Touched — done").
- Cross-checked the captured event shape against docs/research/corpus/
  single-tap.evdev (the corpus is the reference).
- Checked tbard's journal during the same window for a tap log (expect NONE,
  per the source audit: current_bl==0 gate at src/providers/input.rs:471 drops
  the touch before the gesture handler, so no info! tap log at src/main.rs:786).

The event shapes are STRUCTURALLY IDENTICAL (same device, same axes, same
BTN/ABS sequence, same SYN_REPORT framing). Our capture has an extra
ABS_MT_SLOT=9 line at the start (slot assignment) — a normal variant, present
because the kernel had a free slot. POSITION_X differs (11279 vs 8319) because
the touch landed at a different horizontal location on the bar. TRACKING_ID
differs (79 vs 203) because it is a per-touch monotonic counter. Both are valid
single taps in the ABS 32767-space.

## tbard journal during the touch window
  sudo journalctl -u tbard.service --since "2026-09-27 00:30:00"
  → "-- No entries --"
NO tap log line appeared. This is consistent with the source audit (Fact 2):
the current_bl==0 gate at src/providers/input.rs:471 drops the touch event
before it reaches the gesture handler, so no info! tap log (src/main.rs:786-794)
is emitted. The touch is silent in tbard's journal EVEN THOUGH the digitizer
hardware produced a valid event.

## verdict (finding (a) empirically corroborated)
The digitizer hardware IS producing valid single-tap events at the kernel
layer (evtest capture, shape matching the corpus reference). The touch-drop is
IN TBARD'S CODE, not in the hardware:
  - src/providers/input.rs:471 gate: `if ... self.current_bl == 0 { continue; }`
    drops the event because LibinputProvider::current_bl is stuck at 0
    (src/providers/input.rs:89, no setter).
  - Even if the event reached the gesture handler, backlight.notify_activity()
    has zero call sites (src/main.rs:839 calls input.notify_activity() which is
    a no-op at src/providers/input.rs:522-524), so no wake-to-bright would occur.

Both HC2 symptoms ("NO tap log line, NO wake/brighten") are explained by ONE
root cause: the input → backlight wake path is not wired at runtime (Fact 2).

## Stage-4 preview implication
The full real-input chain (ABS 32767-space → scale → hit_test → widget id) is
NOT observable in this run because the touch is dropped before hit_test. The
Stage-4 preview (tap log + no injection) CANNOT be confirmed until the
current_bl==0 gate is fixed (or current_bl is updated from the backlight state)
AND the touch reaches the gesture handler. The digitizer side of the chain
(ABS events) is proven; the tbard-internal side (scale → hit_test → widget id)
is NOT proven on hardware in this run. Stage 4 owes: the input-path fix +
re-verification of the tap log + confirming no uinput key injection from the
default-page widget action (the render-only default page has no widget actions
that inject keys — but this cannot be demonstrated until touches reach the
handler).
