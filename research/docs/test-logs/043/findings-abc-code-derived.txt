## FACT (1) — TAP-LOG LEVEL: `info!` (VISIBLE at RUST_LOG=info)
================================================================================

The tap / widget-hit / gesture log is emitted at **info!** level. It IS visible
under RUST_LOG=info (the level set in the installed unit per ADR-045). So the
"human touched the bar but no tap log appeared" symptom is NOT explained by the
log level being debug!/trace!.

### Exact log:: call sites (tap + swipe observability)

- **Tap log** — `src/main.rs:786-794`:
    Gesture::Tap { x, y } => {
        let hit = pages[active_page].hit_test(x, y);
        info!(
            "tbard: tap page={} logical=({:.0},{:.0}) hit={:?}",
            pages[active_page].id, x, y, hit.as_ref().map(|h| h.widget_id)
        );
  Level: `info!` (imported at `src/main.rs:38` via `use log::{info, warn};`).

- **Horizontal-swipe log** — `src/main.rs:804-817`:
    Gesture::HorizontalSwipe { ... } => {
        info!("tbard: swipe page={} logical=({:.0},{:.0}) delta_x={:.0} hit={:?}", ...);
  Level: `info!`.

### Confirming ADRs
- `docs/adr/020-coordinate-spaces.md:124` — tap path logs an info! line.
- `docs/adr/045-observability-rust-log-info.md:40-46,152-154` — RUST_LOG=info is
  the threshold at which info! lines appear; tap log already at info! in code.

### Verdict
Tap log is at info!. At RUST_LOG=info it is emitted. A missing tap log is NOT a
level-filter issue. (The actual reason no tap log appeared: see Fact 2 — touch
events are dropped before reaching the gesture handler when current_bl==0.)

## FACT (2) — INPUT → NOTIFY_ACTIVITY → UPDATE() WIRING: NOT WIRED (dead path)
================================================================================

The "touch → backlight wake" path is ABSENT at runtime in real mode. Touch
events reach the gesture classifier + key emission but NEVER reset the
backlight's idle timer (notify_activity). A touch does NOT re-brighten the bar
through tbard's adaptive path.

### The runtime input path, hop by hop

Hop 0 — digitizer event read. `LibinputProvider::poll` — `src/providers/input.rs:446-516`.
  GATE at `src/providers/input.rs:471`:
    if Some(te.device()) != self.digitizer || self.current_bl == 0 { continue; }
  A touch event is DROPPED if self.current_bl == 0. current_bl is initialized to
  0 at `src/providers/input.rs:89` and is NEVER updated (no setter; only read via
  current_backlight() at `:518-520`). So once the bar is dark (current_bl==0 in
  the input provider's stale cache), digitizer events are dropped BEFORE they
  reach the gesture handler.

Hop 1 — poll called in render loop. `src/main.rs:737` — let events = input.poll();

Hop 2 — touch contact → gesture state machine. `src/main.rs:761-774` →
  crate::widgets::update_gesture(...) at `src/main.rs:768`.

Hop 3 — gesture classification. `src/widgets/mod.rs:90` update_gesture returns
  (GestureState, Option<Gesture>); quick lift → Gesture::Tap (`:116`).

Hop 4 — tap/swipe handler + key emission (NO backlight call). `src/main.rs:776-827`.
  hit_test (`:787`/`:809`), logs tap/swipe at info! (Fact 1), emits keys via
  emit_keys (`:799-800`). **There is NO backlight.notify_activity() call here.**

  grep over src/ for `backlight\.notify_activity|backlight\.set_brightness|
  backlight\.enable|backlight\.update|backlight\.set_lid_closed` → exactly 5
  matches in src/main.rs:
    `src/main.rs:547`  backlight.enable()         (scanout-begin, once)
    `src/main.rs:835`  backlight.set_lid_closed() (lid event only)
    `src/main.rs:845`  backlight.update()         (loop-bottom, every iteration)
    `src/main.rs:1425`, `:1471`                    (test-module, not runtime)
  **backlight.notify_activity() is NEVER called at runtime.** The override
  exists (`src/providers/backlight.rs:299-301` → inherent `:202-204` which sets
  last_active = Instant::now()) but has zero call sites.

Hop 5 — what InputEvent::Activity DOES call (the WRONG provider). `src/main.rs:838-840`:
    InputEvent::Activity => { input.notify_activity(); }
  This calls notify_activity() on the INPUT provider (I: InputProvider), NOT the
  backlight. LibinputProvider::notify_activity is an INTENTIONAL NO-OP —
  `src/providers/input.rs:522-524`:
    fn notify_activity(&mut self) {
        // Intentionally empty — activity tracking is in backlight
    }
  The comment claims "activity tracking is in backlight," but the code never
  routes activity to the backlight. InputEvent::Activity is produced for non-FN
  keyboard events (`:467`), switch events (`:507`), catch-all (`:510`) — NOT for
  digitizer touch events (those are InputEvent::Touch).

Hop 6 — loop-bottom update() runs unconditionally. `src/main.rs:845` —
  backlight.update(); every loop iteration (~10ms, `src/main.rs:848`). This is
  the adaptive dimmer. It reads self.last_active.elapsed()
  (`src/providers/backlight.rs:223`). last_active is set ONCE at construction
  (`src/providers/backlight.rs:100`, last_active: Instant::now()) and NEVER reset
  by a touch (no notify_activity call). since grows monotonically from process
  start. After 30s → DIMMED_BRIGHTNESS=1; after 60s → 0 (`:226-241`).

### ADRs describing the intended (but unimplemented) adaptive path
- `docs/adr/046-runbook-value-only-probe.md:93-96` — "have the human touch the
  bar first (wake-to-bright: a touch event wakes the bar via tbard's adaptive
  notify_activity path, resetting last_active and re-brightening to
  active_brightness)". ASPIRATIONAL/DESCRIPTIVE — describes intended behavior,
  not implemented wiring. Same ADR `:147-153` hedges with "if tbard's
  notify_activity path handles it" — in the code, it does NOT.
- `docs/adr/043-backlight-enable-write-render-path.md:115-124` — explicitly
  scopes wake/DPMS OUT: "Event-driven re-brightening on wake/DPMS is a FUTURE
  ADR (scope note, not implementation)."
- `docs/adr/044-backlight-provider-dispatch-audit.md:206` — claims notify_activity
  is "(called via input event path)" and "NO DEFECT. Override present." This is
  INCORRECT about the call site — the override is present, but the input event
  path calls input.notify_activity() (no-op), not backlight.notify_activity().
  The audit verified the override exists + dispatches correctly IF CALLED, but
  did not verify any runtime call site on the backlight.

### The wiring verdict (Fact 2)
"touch → backlight wake" is NOT wired at runtime in real mode. Concretely:
  - BacklightProvider::notify_activity override on SysfsBacklight is correct
    (`src/providers/backlight.rs:202-204`, `:299-301`) but DEAD — no call site.
  - InputEvent::Touch arm in real_main (`src/main.rs:761-833`) does not call it.
  - InputEvent::Activity arm (`src/main.rs:838-840`) calls input.notify_activity()
    (input provider, no-op) instead of backlight.notify_activity().
  - Additional gate at `src/providers/input.rs:471` drops touch events when
    self.current_bl == 0, and current_bl on the input provider is STUCK at 0
    (`:89`, no setter) — once the bar is dark, digitizer events are dropped
    before they even reach the gesture handler.

This explains the HC2 observation: "Touching the bar: NO tap log line, NO
wake/brighten." The touch events are dropped at the current_bl==0 gate, so they
never reach the gesture handler (no tap log) and never reset last_active (no
wake). Both symptoms from ONE root cause.

## FACT (3) — SOURCE OF 54 (the +0.72s sysfs probe value)
================================================================================

### (3a) Where does the enable-write value 128 come from?
- `active_brightness` default = 128 — `src/config/yaml.rs:63-65`:
    fn default_brightness() -> u32 { 128 }
  Used by Settings::default (`src/config/yaml.rs:49`) + serde default
  (`src/config/yaml.rs:32-33`).
- Passed to SysfsBacklight::new(true, 128) — `src/main.rs:349`. The `true` is
  `adaptive` (adaptive path IS enabled in real mode). The 128 is HARDCODED at
  the call site (NOT read from the loaded config's active_brightness field —
  the config's value is never threaded into SysfsBacklight::new; only the
  default 128 is used). Stored at `src/providers/backlight.rs:103`.
- enable() writes active_brightness.min(max_bl) = 128 — `src/providers/backlight.rs:175-199`,
  value computed at `:176`:
    let value = self.active_brightness.min(self.max_bl);  // 128.min(255) = 128
  Journal line at `:180-185`:
    log::info!("tbard: backlight enable-write {} (max {}, active_brightness {})", value, ...);

### (3b) Where does 54 come from? — the adaptive display_to_touchbar curve
54 = display_to_touchbar(display_brightness≈90, active_brightness=128).

- display_to_touchbar — `src/providers/backlight.rs:159-163`:
    fn display_to_touchbar(display: u32, active_brightness: u32) -> u32 {
        let normalized = display as f64 / MAX_DISPLAY_BRIGHTNESS as f64;  // 509 (backlight.rs:16)
        let adjusted = (normalized.powf(0.5) * active_brightness as f64) as u32 + 1;  // sqrt
        adjusted.min(MAX_TOUCH_BAR_BRIGHTNESS)  // min 255
    }
  With active_brightness=128 and display=90:
    (sqrt(90/509) * 128) as u32 + 1 = (0.42037 * 128) as u32 + 1 = (53.81) as u32 + 1 = 54

- Called from update() — `src/providers/backlight.rs:222-241`:
    pub fn update(&mut self) -> bool {
        let since = self.last_active.elapsed().as_millis() as u64;
        let new_bl = self.max_bl.min(if self.lid_closed {
            0
        } else if since < BRIGHTNESS_DIM_TIMEOUT_MS {   // 30_000 (backlight.rs:17)
            if self.adaptive {                          // true (main.rs:349)
                let brightness = self.display_bl_path.as_ref()
                    .and_then(|p| read_attr(p, "brightness").ok())
                    .unwrap_or(self.max_bl / 2);
                Self::display_to_touchbar(brightness, self.active_brightness)   // ← 54
            } else { self.active_brightness }           // 128 (non-adaptive)
        } else if since < BRIGHTNESS_OFF_TIMEOUT_MS {   // 60_000 (backlight.rs:18)
            DIMMED_BRIGHTNESS                          // 1 (backlight.rs:19)
        } else { 0 });
  On the first tick after enable(), since is tiny (<30s), adaptive is true,
  display_bl_path is Some (discovered at `:65`), and the read of the main
  display brightness yields 90 → display_to_touchbar(90, 128) = 54.

- update() then WRITES 54, overwriting the 128 from enable(). At `:243-265`:
  after enable() set current_bl = 128 (`:179`), the first update() computes
  new_bl = 54. Since current_bl (128) != new_bl (54), the gate at `:243`
  (if self.current_bl == new_bl { return false; }) does NOT short-circuit, and
  set_backlight_file(54) is called at `:249`. current_bl becomes 54 (`:251`).
  **This is why the sysfs read within <1s shows 54, not 128.**

### (3c) Adaptive dimmer — first-tick target ~54, NOT a ramp from 128
The dimmer is NOT a gradual ramp/step-down; it is a STEP FUNCTION keyed on
last_active.elapsed():
- Constants — `src/providers/backlight.rs:17-19`:
    BRIGHTNESS_DIM_TIMEOUT_MS = 30_000  // 30s
    BRIGHTNESS_OFF_TIMEOUT_MS = 60_000  // 60s
    DIMMED_BRIGHTNESS         = 1
- Curve (`:224-241`):
    since < 30s AND adaptive → display_to_touchbar(display_bl, 128) ≈ 54
        ← FIRST-TICK TARGET, applied IMMEDIATELY on the first update() tick
          (~10ms after enable(), src/main.rs:848). NO "hold 128 for N seconds
          then decay" behavior. The 128 from enable() is overwritten on the
          very first loop-bottom update() tick.
    30s ≤ since < 60s → DIMMED_BRIGHTNESS = 1
    since ≥ 60s → 0

So the dimming "curve" is: 128 (enable) → ~54 (immediately, first update tick)
→ 1 (at 30s) → 0 (at 60s), with no input ever resetting last_active (Fact 2).
The 54→1→0 portion after 30s is ALSO reinforced by the kernel-side appletbdrm
driver's own auto-dim (ADR-046:77-87, citing s039 S2).

### (3d) Other candidate sources of 54 — ruled in/out
| Candidate | Location | Value | Is it 54? |
|---|---|---|---|
| Adaptive display_to_touchbar(90,128) first-tick target | `backlight.rs:159-163`, `:227-233` | sqrt(90/509)*128+1 ≈ 54 | **YES — the source** |
| active_brightness default | `config/yaml.rs:63-65` | 128 | No (enable-write value) |
| max_bl / 2 fallback (display-bl read fail) | `backlight.rs:232` | 127 → display_to_touchbar(127,128)=65 | No |
| DIMMED_BRIGHTNESS (30-60s idle) | `backlight.rs:19` | 1 | No |
| FAILSAFE_BRIGHTNESS (write failure) | `backlight.rs:23` | 1 | No |
| MAX_TOUCH_BAR_BRIGHTNESS | `backlight.rs:15` | 255 | No |
| MAX_DISPLAY_BRIGHTNESS | `backlight.rs:16` | 509 | No (denominator in 54 math) |
| Oracle's ported curve (ancestry) | `backup_old/tiny-dfr-mbp142/src/backlight.rs:96-101` | same sqrt(d/509)*active+1 | Same emergent 54, not a separate constant |
| appletbdrm kernel auto-dim (post-54 decay) | ADR-046:77-87 (s039 S2) | decays 54→1→0 over 30-60s | Explains 54→0 decay, not the 54 itself |

### (3e) Math VERIFIED on-hardware
Measured display backlight (acpi_video0) at time of probe: brightness=90, max=90.
python3: sqrt(90/509)*128+1 = 54. **CONFIRMED — 54 is the adaptive curve output
at display brightness 90, NOT a write failure.**

## CROSS-CUTTING SUMMARY
================================================================================
Fact 1: tap log is info! (src/main.rs:786-794, :804-817) — visible at RUST_LOG=info.
        A missing tap log is NOT a level-filter issue.

Fact 2: backlight.notify_activity() has ZERO call sites in src/. The only
        notify_activity call (src/main.rs:839) targets the input provider, whose
        impl is an intentional no-op (src/providers/input.rs:522-524). Touch →
        backlight wake is NOT wired at runtime. Additionally
        LibinputProvider::current_bl is stuck at 0 (src/providers/input.rs:89,
        no setter) and the gate at src/providers/input.rs:471 drops touch events
        when current_bl == 0 — so once the bar is dark, touches are dropped
        before reaching the gesture handler (no tap log) AND never reset
        last_active (no wake). Both HC2 symptoms from ONE root cause.

Fact 3: 128 comes from default_brightness()=128 (src/config/yaml.rs:63-65) →
        SysfsBacklight::new(true, 128) (src/main.rs:349) → enable() writes 128
        (src/providers/backlight.rs:176-185). 54 is the adaptive
        display_to_touchbar(90,128) first-tick target (src/providers/backlight.rs:159-163,
        called at :233), which update() writes immediately (:249) because
        current_bl(128) != new_bl(54). The strict +1s=128 acceptance criterion
        is SUPERSEDED: the enable-write (128) is real and logged, but the
        adaptive loop's first update() tick (~10ms later) overwrites it with the
        curve output (54). The write PATH is proven (journal line + luminance
        followed tbard's own writes 128→54→0); the +1s=128 VALUE is not
        achievable given the current adaptive design.

## ADR PROPOSALS (no fixes on the air)
================================================================================
- ADR-047 (proposed): wire touch → backlight.notify_activity() at runtime.
  The InputEvent::Touch arm (src/main.rs:761-833) should call
  backlight.notify_activity() (not input.notify_activity()). This is the
  wake-to-bright path ADR-046:93-96 describes aspirationally. Also: update
  LibinputProvider::current_bl from the backlight's current_backlight() each
  poll, OR remove the current_bl==0 gate at src/providers/input.rs:471, so
  touches are not dropped when the bar is dark. Coordinate with ADR-044's
  incorrect "NO DEFECT" claim about the notify_activity call site.

- ADR-048 (proposed): enable-write vs adaptive-loop coordination. Either
  (a) hold the enable-write value (128) for a grace period before the adaptive
  update() may overwrite it, OR (b) make enable() set last_active = now() so
  the first update() tick computes display_to_touchbar(display, 128) = 54
  deliberately (acknowledging 54 is the intended "on, adaptive" level, not 128),
  OR (c) reframe the acceptance criterion: the enable-write's job is to confirm
  the write PATH (journal line + luminance follows tbard's writes), NOT to hold
  a specific sysfs value for +1s. The +1s=128 criterion in the runbook is
  superseded by the adaptive design.

- Erratum (D-027-1): manual §7 / s039 "kernel-side decay" was the oracle's
  adaptive loop (same display_to_touchbar curve, backup_old/tiny-dfr-mbp142/
  src/backlight.rs:96-101), NOT a kernel-side auto-dim. Finding (c) confirmed:
  manual brightnessctl 50 held 10+ min with tbard running quiet (cache==target
  → no writes) — NO kernel auto-dim. Annotate manual §7 + ADR-046:77-87.

- ADR-044 correction: the dispatch audit's claim that notify_activity is
  "(called via input event path)" and "NO DEFECT" (adr/044:206) is incorrect
  about the call site. The override is present + dispatches correctly IF CALLED,
  but no runtime call site on the backlight exists. Re-audit needed.
