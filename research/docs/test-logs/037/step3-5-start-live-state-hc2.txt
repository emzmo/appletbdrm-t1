=== DEFECT ANALYSIS — ADR-043 enable-write is dead code (trait-default dispatch) ===
  Root cause (read-only source analysis; NO fix applied — FREEZE on src/):
  1. `BacklightProvider::enable()` has a DEFAULT no-op impl returning `Ok(())`
     (src/providers/mod.rs:120-122):
         fn enable(&mut self) -> anyhow::Result<()> { Ok(()) }
  2. `SysfsBacklight` has an INHERENT `pub fn enable(&mut self)` (backlight.rs:175)
     that performs the actual ADR-043 write (value=active_brightness.min(max_bl),
     via the held fd, with INFO success / ERROR fail-safe logging).
  3. `impl BacklightProvider for SysfsBacklight` (backlight.rs:269-...) overrides
     set_brightness, brightness, max_brightness, update, notify_activity,
     set_lid_closed — but does NOT override `enable()`.
  4. The call site `real_main` is generic: `backlight: &mut B where B: BacklightProvider`
     (main.rs:502-513). The call `backlight.enable()` (main.rs:547) dispatches
     through the TRAIT, so it resolves to the trait's DEFAULT no-op — NOT the
     inherent `SysfsBacklight::enable()`. (Rust: inherent methods take priority
     only on concrete-typed calls, NOT through a generic/trait bound.)
  5. Therefore the ADR-043 enable-write NEVER executes. The inherent method is
     dead code. Its unit tests (backlight.rs:379-508) call `bl.enable()` on a
     CONCRETE `SysfsBacklight`, so they exercise the inherent method and PASS —
     masking the trait-dispatch gap. The integration test at main.rs:1435 uses
     a `RecordingBacklight<B>` wrapper whose `enable()` (main.rs:1363 area)
     forwards to `self.inner.update()` (NOT `self.inner.enable()`) — so it also
     does not catch the missing trait override. (To be re-confirmed in the ADR;
     recorded here as the likely reason CI did not catch this.)

  Why the panel is dark (the full chain):
  - `SysfsBacklight::new` (backlight.rs:88-99) initializes `current_bl` to the
    sysfs-read value at construction = 54 (the oracle's boot-time D3 write).
  - `enable()` (trait no-op) does NOT write 128 and does NOT update `current_bl`
    → `current_bl` stays 54.
  - The render loop calls `backlight.update()` every 10ms (main.rs:845).
    `update()` computes `new_bl` = adaptive curve: `display_to_touchbar(
    acpi_video0.brightness=90, active_brightness=128)` with
    MAX_DISPLAY_BRIGHTNESS=509 → `sqrt(90/509)*128+1` = `0.4205*128+1` ≈ 54.
    `new_bl(≈54) == current_bl(54)` → the `if current_bl == new_bl { return
    false; }` gate (backlight.rs:243-245) makes `update()` a NO-OP — no write.
  - This is EXACTLY the session-033 stale-read coincidence that ADR-043 was
    designed to break — but ADR-043's breaker (the unconditional `enable()`
    write of 128) is dead code via trait-default dispatch, so the coincidence
    is unbroken. The dark panel persists by the same mechanism, with the
    intended fix inert.
  - The 54→0 transition in the sysfs READ value is the appletbdrm driver
    resetting the hardware on the oracle's master release (kernel-side, no
    userspace write, hence mtime unchanged). tbard then neither wrote 128
    (enable no-op) nor corrected the 0 (update gated on stale current_bl=54).

  Defect class: ADR-043 enable-write dead-code via trait-default dispatch.
    Distinct from attempt #3's "never-held-fd / never-wrote" framing: here the
    fd IS held (fd 23 -> brightness, verified) and the inherent write method
    EXISTS and is unit-tested, but the production call path routes to the
    trait default because the `impl BacklightProvider for SysfsBacklight`
    block omits the `enable()` override. ADR-043 landed the method on the
    wrong impl surface (inherent vs trait).

  Proposed ADR (no fix on the air): ADR-044 — "ADR-043 enable-write must
    override the `BacklightProvider` trait method, not add an inherent method."
    Fix surface: add `fn enable(&mut self) -> anyhow::Result<()> { SysfsBacklight::enable(self) }`
    to `impl BacklightProvider for SysfsBacklight` (backlight.rs:269), mirroring
    the existing `update`/`notify_activity`/`set_lid_closed` forwarding pattern
    (backlight.rs:293-303). Regression guard: an integration test that calls
    `backlight.enable()` through a `&mut dyn BacklightProvider` (trait object)
    and asserts the write occurred — the current tests call on a concrete type
    and so miss the gap. Also: set `Environment=RUST_LOG=info` (or a tbard-
    specific filter) in tbard.service so the boot sequence is observable in
    the journal on the next validation run (the INFO-suppression made this run
    partially blind; the defect was inferable only from sysfs+debugfs+source).
